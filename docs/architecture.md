# Architecture and implementation coverage

## Scope

Build the actual AI video-making workflow in `Ikz7867/toon`. The user explicitly corrected the PDF's mistaken photo-wall interpretation. Requirements from other conversations are excluded.

## Runtime

The browser studio is a dependency-free ES module application. A Node 24 server owns authentication, project records, assets and background jobs. SQLite runs in WAL mode. One serial engine worker processes a persisted job snapshot so subsequent project edits do not change an in-flight render.

The core library files are deliberately separate: `domain.mjs` validates provider-compatible input; `provider.mjs` contains the optional fal integration; `local-provider.mjs` connects the default self-hosted worker; `engine.mjs` controls lifecycle; `media.mjs` owns FFmpeg; `app.mjs` exposes HTTP; `store.mjs` owns persistence; `auth.mjs` handles single-owner sessions.

## Pipeline

1. Save a validated project and one to eight scene specifications.
2. Generate an immutable render snapshot using an idempotency key. Reject a second concurrent render for the same project.
3. For each scene, use its imported video, or submit text/image-conditioned inference to the provider.
4. Save `submitting` **before** the remote call. Save the returned request ID and operation URLs immediately after it returns.
5. Poll that saved request. In fal mode download only from permitted HTTPS media hosts after provider completion. In local mode download only from the exact configured GPU service origin; never trust a provider-supplied download URL. Do not expose or forward provider authorization to media downloads.
6. Validate the generated video, normalize dimensions, frame rate and audio, and optionally burn the scene caption.
7. Concatenate compatible H.264 clips, optionally replace audio with the uploaded narration, write SRT, and inspect the actual output before marking completion.
8. Stream the finished MP4 through authenticated routes supporting HTTP byte ranges.

The UI progress bar represents completed pipeline stages. It is not an invented GPU completion percentage.

## Persistence

| Table | Purpose |
| --- | --- |
| `projects` | Editable project JSON and update timestamp |
| `jobs` | Immutable project snapshot, job state, scene state, request handles and output metadata |
| `assets` | Validated upload metadata and generated local filenames |
| `characters` | Reusable name, description, and reference-image asset |

Media lives outside the web root. UUID filenames are generated by the server. Static routing is an explicit allowlist; `.env`, SQLite and arbitrary filesystem paths are not served.

## Recovery and failure semantics

- `queued`: persisted and waiting for the single engine worker.
- `running`: submitting, polling, downloading, normalizing or assembling.
- `completed`: final output exists and has been inspected.
- `failed`: explicit failure; a resume keeps existing provider handles and finished scenes.
- `needs_review`: submission outcome is uncertain; no automatic paid retry.
- `cancelled`: local work stopped; remote cancellation is best-effort.

A restart returns interrupted known requests to the queue. An interrupted fal `submitting` state without a request handle is quarantined for review. Local submissions are replay-safe: the GPU worker persists a unique key derived from the studio job and scene, so an interrupted submit is retried under the same ID. Jobs also record their backend identity to prevent accidental provider switching during a resume. The current design intentionally uses a single worker process; it does not yet implement distributed leases across multiple hosts.

## Next production gates

Before relying on the service for production, run real 5-second text-to-video and image-to-video smoke tests on the intended GPU. For optional fal mode, run the equivalent provider-account smoke tests. Confirm result-host compatibility, validate image conditioning, and inspect output quality. Run a live Ollama script test if enabling it. Deploy the container to the selected persistent host, confirm HTTPS/session behavior, exercise the interface on mobile and desktop, and establish disk monitoring/backups. A multi-tenant service requires a separate identity, ownership, quotas and distributed queue design.


## Self-hosted worker

`gpu_service/service.py` is an authenticated Python HTTP API with its own SQLite queue. It runs one isolated `runner.py` process per request. Each process loads local safetensors through pinned Diffusers/PyTorch dependencies, runs Wan inference, and writes an MP4. The model is reloaded for each request to release GPU memory reliably and make cancellation terminate the actual process. This costs load time but avoids shared-pipeline mutation between jobs. The worker kills the process group on cancellation/timeout and validates its output with FFprobe before declaring completion.

Inference does not call fal or a hosted model API. `download_model.py` downloads public model files once and records the exact resolved model revision; runner processes use offline mode and `local_files_only=True`. There is no production mock-inference mode. Tests inject a separate FFmpeg fixture explicitly.

The local profile generates 121 frames at 24 fps. The existing assembly layer trims this to exactly five seconds. Dimensions are multiples of 32; 1080p exports are resized from 704-line inference. Wan TI2V generates visual footage without native audio. Imported audio or narration still works in the assembler.
