# Architecture and implementation coverage

## Scope

Build the actual AI video-making workflow in `Ikz7867/toon`. The user explicitly corrected the PDF's mistaken photo-wall interpretation. Requirements from other conversations are excluded.

## Runtime

The browser studio is a dependency-free ES module application. A Node 24 server owns authentication, project records, assets and background jobs. SQLite runs in WAL mode. One serial engine worker processes a persisted job snapshot so subsequent project edits do not change an in-flight render.

The core library files are deliberately separate: `domain.mjs` validates provider-compatible input; `provider.mjs` contains the fal integration; `engine.mjs` controls lifecycle; `media.mjs` owns FFmpeg; `app.mjs` exposes HTTP; `store.mjs` owns persistence; `auth.mjs` handles single-owner sessions.

## Pipeline

1. Save a validated project and one to eight scene specifications.
2. Generate an immutable render snapshot using an idempotency key. Reject a second concurrent render for the same project.
3. For each scene, use its imported video, or submit text/image-conditioned inference to the provider.
4. Save `submitting` **before** the remote call. Save the returned request ID and operation URLs immediately after it returns.
5. Poll that saved request. Download only from permitted HTTPS media hosts after provider completion. Do not expose or forward provider authorization to media downloads.
6. Validate the generated video, normalize dimensions, frame rate and audio, and optionally burn the scene caption.
7. Concatenate compatible H.264 clips, optionally replace audio with the uploaded narration, write SRT, and inspect the actual output before marking completion.
8. Stream the finished MP4 through authenticated routes supporting HTTP byte ranges.

The UI progress bar represents completed pipeline stages. It is not an invented GPU completion percentage.

## Persistence

| Table | Purpose |
| --- | --- |
| `projects` | Editable project JSON and update timestamp |
| `jobs` | Immutable project snapshot, job state, scene state, request handles and output metadata |
| `assets` | Validated upload metadata and generated local filenames |
| `characters` | Reusable name, description, and reference-image asset |

Media lives outside the web root. UUID filenames are generated by the server. Static routing is an explicit allowlist; `.env`, SQLite and arbitrary filesystem paths are not served.

## Recovery and failure semantics

- `queued`: persisted and waiting for the single engine worker.
- `running`: submitting, polling, downloading, normalizing or assembling.
- `completed`: final output exists and has been inspected.
- `failed`: explicit failure; a resume keeps existing provider handles and finished scenes.
- `needs_review`: submission outcome is uncertain; no automatic paid retry.
- `cancelled`: local work stopped; remote cancellation is best-effort.

A restart returns interrupted known requests to the queue. An interrupted `submitting` state without a request handle is quarantined for review. The current design intentionally uses a single worker process; it does not yet implement distributed leases across multiple hosts.

## Implemented vs. dependent vs. not implemented

| Capability | Status |
| --- | --- |
| Text-to-video / image-to-video | Real fal REST adapter implemented; live credentials and provider smoke test required |
| Scene editor / reorder / styles / formats | Implemented |
| Saved character descriptions and references | Implemented; model consistency is probabilistic |
| AI storyboard writing | Ollama adapter implemented; reachable model required, not live-tested |
| MP4 import, normalization and multi-scene export | Implemented and tested with actual FFmpeg output |
| Silent export, source audio, narration upload | Implemented; silent and source-audio output tested |
| Captions and SRT export | Implemented and tested |
| Saved jobs, idempotency, recovery, cancellation | Implemented and tested |
| Single-owner login and guarded media/API routes | Implemented and tested |
| Multi-model marketplace, billing and credits ledger | Not implemented |
| Voice synthesis, voice cloning and lip-sync engine | Not implemented; narration import is supported |
| Text-to-image generation or automatic reference-image generation | Not implemented; reference upload is supported |
| Frame-accurate timeline, trimming handles, transitions | Not implemented; sequential scene composition only |
| Train or self-host video model weights on own GPUs | Not implemented; video inference uses fal |
| Multi-tenant accounts, teams and public sharing | Not implemented |
| Native mobile applications | Not implemented; responsive browser UI supplied |
| Production server deployment | Not performed in this environment |
| Browser visual verification | Not performed in this environment |

## Next production gates

Before relying on the service for production, run a real paid 5-second text-to-video and image-to-video smoke test using the intended fal account. Confirm result-host compatibility, validate image conditioning, and inspect output quality. Run a live Ollama script test if enabling it. Deploy the container to the selected persistent host, confirm HTTPS/session behavior, exercise the interface on mobile and desktop, and establish disk monitoring/backups. A multi-tenant service requires a separate identity, ownership, quotas and distributed queue design.
